# OCR 근거 기반 5항목 LLM 검토

2026-09-07 사용자 승인: 정확도를 우선하고 속도는 다음 순위로 둔다. 기존 날짜·함량 후보 선택을 약명·함량·1회량·횟수·일수의 근거 기반 검토로 확장한다.

## 범위와 고정 결정

- 작업 대상은 `906/AH_05_05` 로컬 복사본이다. 기존 사용자 변경을 보존하고 Git 변경 작업, 실행 중 서비스 재시작, DB/API 스키마 변경은 하지 않는다.
- OCR은 기존 CLOVA 결과를 사용한다. 이미지 추가 전송, 의약품 지식으로 빈칸 추측, 외부 약품 DB 도입은 범위 밖이다.
- 기존 개인정보 제외 로직을 유지한다. 약물 행에 연결된 근거와 해당 행 주변의 함량 문맥만 제공하며 환자 정보와 OCR 원문을 평가 산출물에 저장하지 않는다.
- LLM은 모든 확인 가능한 약물 행의 5항목을 검토한다. 필드마다 원문 발췌와 근거 ID, supported/uncertain/absent 상태를 반환한다.
- 서버는 ID 존재·중복·행 소속·필드 적합성·원문 일치·숫자 경계·허용 범위를 확인한다. 정규화는 서버가 수행한다. 잘못된 제안은 적용하지 않고 확인 필요 사유를 남긴다.
- 기존 규칙 결과는 실패 시 fallback이다. 유효한 수정은 기존 규칙의 선택과 다르더라도 반영할 수 있다. LLM 실패·누락·판단 불가를 성공한 검토로 표시하지 않는다.

## 구조

기존 legacy 계약을 비교군으로 유지하고 semantic 계약을 추가한다. 동일한 공급자와 분석 경로에서 모드에 따라 입력과 검증을 선택한다. 검증 후에는 기존 MedicationRowsResult/GroundedResult로 돌아와 기존 공개 응답과 근거 표시를 재사용한다.

후보 생성은 현재 약물 행과 좌표를 사용한다. 행 경계를 넘는 근거를 차단하며 명확한 행 귀속이 없는 내용은 보내지 않는다. 문서에서 행 자체가 탐지되지 않거나 재촬영 판정된 경우는 이번 LLM 단계만으로 복구한다고 주장하지 않는다.

## 수용 기준

1. 5항목 모두 검토 입력·선택·서버 검증·공개 응답·근거 진단까지 연결된다.
2. 원문에 없는 값, 숫자 일부 자르기, 다른 행 근거, 개인정보, 중복/누락/실패 응답에 대한 회귀 테스트가 통과한다.
3. 동일 OCR 입력을 사용하는 no-LLM / legacy / semantic 비교를 수행한다. 개선은 복구 정답과 새 오답을 구분해 보고한다.
4. `test.jpg` 기존 31/33의 누락 함량 2개 복구를 목표로 하되, 실제 결과를 그대로 기록한다. 16개 자료의 보정된 정답·평가 상태를 고정하고 전체 정확도 상승과 오답 비증가를 승격 기준으로 삼는다.
5. 지연은 호출별 실측하고 서비스 전체 실측과 OCR 재사용 후처리 시간을 구분한다. 개선 폭은 실험 전 확정하지 않는다.
6. 필수 검증과 독립 검토가 끝나고 기준을 충족하면 종료한다. 기준을 충족하지 못하면 기본 동작에 무리하게 승격하지 않고 남은 원인과 실험 결과를 명시한다.

## 재개 및 산출물

코드·테스트·실험을 원자 단위로 나눈다. 실험은 문서 1개 단위로 해시 봉투를 원자 저장하며 입력·설정·소스·정답의 동일성을 확인한다. 손상되거나 다른 설정의 체크포인트는 거부한다. OCR 원문은 프로세스 메모리에만 두므로 중간 문서가 중단되면 그 문서만 다시 호출한다.
