# 복약메모 진료용 챗 요약 설계

## 목적

사용자가 짧은 진료 시간 안에 최근 복약 이력과 복약 중 기록한 증상·변화를 간결하게 설명할 수 있도록 한다. 이 기능은 약물 부작용, 원인, 안전성, 진단을 판단하지 않는다. 사용자가 저장한 복약메모의 사실만 정리한다.

## 범위

- 채팅에서 사용자가 복약메모 정리를 명시적으로 요청했을 때만 실행한다.
- 기본 조회 범위는 요청 시점 기준 최근 6개월이다.
- 현재 및 종료된 진료 건(`CareEpisode`)을 모두 포함한다.
- 메모가 있는 진료 건만 포함하고, 가장 최근 메모 일시 기준으로 최대 3건을 출력한다.
- 사용자가 `전체 기록`, `이전 진료`, 기간을 명시하면 기본 6개월/3건 제한을 확장한다.
- 약물과 연결된 메모와 연결되지 않은 메모를 모두 포함한다.
- 생성 결과는 일반 Assistant 채팅 응답으로 반환되어 기존 `chat_messages.content`에 저장된다.

## 비범위

- `medication_note_summaries` 같은 별도 요약 테이블을 만들지 않는다.
- 원본 `medication_notes`를 수정하거나 LLM 요약문으로 덮어쓰지 않는다.
- RAG 근거 검색, 약물 상호작용 판단, 이상반응 판정, 의학적 권고를 하지 않는다.
- 메모 내용만으로 약물과 증상의 인과관계를 만들지 않는다.

## 선택한 구조

`ConversationGate`는 메모 요약 요청을 식별하는 역할만 수행한다. 실제 조회·정리·요약은 전용 `MedicationNoteSummaryUseCase`와 `MedicationNoteSummaryGenerator`가 담당한다.

```text
사용자 채팅 요청
  -> Conversation Gate: MEDICATION_NOTE_SUMMARY 분류
  -> MedicationNoteSummaryUseCase
     -> MedicationNote / CareEpisode / Medication 조회
     -> 기간·진료 건 수 결정
     -> LLM 사실 요약
  -> 일반 채팅 Assistant 응답
  -> chat_messages.content 저장
```

기존 약·영양제 RAG 경로에 이 기능을 섞지 않는다. 복약메모는 공개 의학 근거가 아니라 사용자의 개인 기록이므로, 조회 대상·안전 정책·출력 계약이 다르기 때문이다.

## 데이터 조회 계약

기존 `medication_notes`를 그대로 사용한다.

- 사용자 소유 메모만 조회한다.
- `care_episode_id`로 메모를 진료 건에 묶는다.
- 각 진료 건의 `alias`, `hospital_name`, 날짜와 `medications`를 함께 읽는다.
- 진료 건 제목은 `별칭 -> 병원명 -> 진료 시작일` 순서로 fallback 한다.
- 진료 건 정렬 기준은 그 진료 건에 속한 가장 최근 `MedicationNote.dosed_at` 내림차순이다.
- 건 내부 메모는 `dosed_at` 오름차순으로 제공한다.
- medication FK가 비어 있더라도 메모는 제외하지 않는다.

기본 모드에서 최근 6개월 내 최근 3건까지만 LLM 입력으로 전달한다. 전체 이력 요청도 입력 크기 제한을 넘을 수 있으므로, 구현 시 최대 메모 수와 최대 원문 길이를 명시적으로 제한하고 잘린 범위를 사용자에게 알린다.

## LLM 요약 계약

LLM에는 아래 정보만 전달한다.

- 진료 건 식별용 제목
- 해당 진료 건의 약물명 목록
- 날짜순 원본 메모
- 출력 언어와 엄격한 사실 요약 규칙

LLM은 JSON Schema로 아래만 반환한다.

- 진료 건별 날짜 메모 bullet 목록
- 진료 건별 한줄 요약

서버는 반환된 진료 건 ID가 입력 진료 건 목록에 속하는지, 메모 ID가 입력 범위를 벗어나지 않는지 검증한다. 모델이 만든 진료 건·약물·날짜·의학적 판단은 폐기하거나 생성 실패로 처리한다.

프롬프트 규칙은 다음을 강제한다.

- 기록된 증상·변화·사실만 압축한다.
- `부작용`, `원인`, `약물 때문에`, `안전`, `위험`, `권장` 같은 판단 표현을 사용하지 않는다.
- 약물과 직접 연결되지 않은 기록도 증상 사실로 포함하되, `약물 연결 없음` 같은 내부 상태를 사용자에게 노출하지 않는다.
- 원문에 없는 약물명·증상·날짜를 만들지 않는다.

## 출력 계약

진료 건 하나는 아래 형식을 사용한다.

```md
💉 **과거 복약 정보 · A병원 진료**

- 타이레놀정
- 리바록사반정

---

📝 **복약메모 요약**

- 9월 3일: 두통이 지속된다고 기록함.
- 9월 5일: 멍이 쉽게 든다고 기록함.
- 9월 7일: 속쓰림과 어지러움을 기록함.

⭐️ **한줄 요약**
복용 기간 중 두통, 멍, 속쓰림과 어지러움 증상을 기록함.

※ 위 내용은 사용자가 기록한 사실을 요약한 것이며, 약물과의 관련성을 판단한 내용은 아닙니다.
```

여러 진료 건은 위 블록을 반복하고, 진료 건 사이에 Markdown 구분선을 둔다. 기본 범위에서 3건을 초과한 경우 마지막에 아래 안내를 붙인다.

```md
📌 최근 3건의 진료 기록만 정리했습니다. 이전 진료 기록도 필요하면 말씀해 주세요.
```

최근 6개월에 메모가 없으면 사실만 간결히 안내한다.

```md
📝 최근 6개월 동안 기록된 복약메모가 없습니다.
```

## 오류 및 안전 처리

- 조회할 메모가 없으면 LLM을 호출하지 않는다.
- LLM 호출 실패 또는 계약 검증 실패 시 원본 메모를 장황하게 그대로 출력하지 않는다. 재시도를 안내하거나, 날짜별 원문을 제한된 개수로 보여주는 안전한 결정론적 fallback을 사용한다.
- 이 기능은 의료 조언이 아니므로 RAG의 `GroundedClaimValidator` 의료 주장 검증 대신, 메모 사실성·출력 계약 검증을 적용한다.
- 기존 응급·민감 요청 차단 경로는 변경하지 않는다.

## 검증 계획

1. 최근 6개월의 현재·종료 에피소드가 함께 조회되는지 확인한다.
2. 최근 메모 기준 3건만 선택되고 네 번째 진료 건 존재 시 안내문이 붙는지 확인한다.
3. 약물 FK가 없는 메모도 결과에 포함되는지 확인한다.
4. 생성 결과가 원문에 없는 약물·증상·날짜·인과관계를 만들면 실패 처리되는지 확인한다.
5. 명시적 요약 요청만 `MEDICATION_NOTE_SUMMARY`로 분류되고, 일반 약 질문은 기존 RAG 경로를 유지하는지 확인한다.
6. 결과가 일반 Assistant 메시지로 저장되고 새 요약 테이블이 생기지 않는지 확인한다.

- 관련 단위·통합 테스트
