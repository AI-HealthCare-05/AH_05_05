# #111 챗봇 세션 유지·목록 관리 프론트 설계

작성일: 2026-08-26  
범위: `frontend/`만 수정  
제외: ERD, 백엔드 모델·라우터·서비스, 실 API 계약 변경

## 목표

- 챗봇에서 다른 하단 탭으로 이동했다 돌아오면 사용하던 대화를 유지한다.
- 페이지 새로고침이나 브라우저/PWA 재실행 뒤에는 저장된 대화가 있으면 최신순 목록을 먼저 보여준다.
- 저장된 대화가 없으면 목록을 거치지 않고 기존 시작 가이드가 있는 새 채팅창을 보여준다.
- 새 채팅과 여러 대화 정리를 모바일과 마우스 환경 모두에서 조작할 수 있게 한다.
- 현재는 목업 저장소로 전체 화면을 검증하되, 나중에는 화면을 바꾸지 않고 `entities/chat`의 구현만 실 API로 교체할 수 있게 한다.

## 비목표

- 백엔드 엔드포인트 경로와 요청·응답 DTO를 확정하지 않는다.
- `ChatSession`, `ChatMessage` ERD나 백엔드 코드를 수정하지 않는다.
- AI 제목 생성, 제목 직접 수정, 검색, 즐겨찾기, 보관함은 만들지 않는다.
- 길게 누르기를 필수 조작으로 만들지 않는다.
- 실제 사용자 대화를 운영 환경의 `localStorage`에 저장하지 않는다.

## 현재 문제

`ChatPage`가 `messages`와 `conversationId`를 컴포넌트 내부 `useState`에만 보관한다. 다른 탭으로 이동하면 컴포넌트가 언마운트되고, 다시 들어올 때 두 값이 초기화된다. 기존 `historyLoader`는 단일 이력만 받을 수 있고 세션 목록이나 현재 세션 선택 개념은 없다.

## 상태 원칙

대화 데이터의 원본과 현재 앱 실행 중 선택 상태를 분리한다.

- 세션과 메시지의 원본: `entities/chat` 저장소
- 현재 앱 실행 중인 세션 ID: 라우터보다 위에 있는 React Context 메모리
- 입력 중인 초안: 채팅방 컴포넌트의 로컬 상태
- 목업 검증용 DB 대체물: `api.mock.ts`의 전용 `localStorage` 저장소
- 실 API 연결 후: 목업 `localStorage` 경로를 사용하지 않고 서버 응답만 사용

React Context는 탭 이동 중 유지되지만 새로고침하면 초기화된다. 따라서 별도의 브라우저 종료 감지 없이 다음 규칙을 만족한다.

| 진입 상황 | 표시 화면 |
|---|---|
| 같은 앱 실행 중 활성 세션이 있음 | 해당 채팅방 |
| 새로고침·재실행 후 저장 세션이 있음 | 채팅 목록 |
| 새로고침·재실행 후 저장 세션이 없음 | 새 채팅창 |
| 목록에서 세션 선택 | 선택한 채팅방 |
| `+` 선택 | 새 채팅창 |

## 화면 구조

기존 `/chat` 라우트 하나를 유지한다. `ChatPage`가 진입 상태를 판정하고 목록과 채팅방 중 하나를 표시한다. 세션별 신규 라우트는 이번 프론트 목업 범위에서 추가하지 않는다. 이렇게 하면 `/chat` 새로고침이 항상 목록 진입 규칙을 거친다.

### 채팅 목록

헤더:

```text
AI 상담                         +  선택
```

행:

```text
지금 먹는 약을 같이 먹어도 되나요?   첫 사용자 메시지, 1줄 말줄임
함께 복용할 때는 다음 사항을...       마지막 메시지, 1줄 말줄임
오늘 오후 3:24
```

- `lastMessageAt` 내림차순으로 고정한다.
- 제목은 첫 사용자 메시지에서 파생한다. 별도 제목 입력이나 AI 제목은 만들지 않는다.
- 마지막 메시지만 제목으로 쓰지 않는다. 답변 때마다 행의 식별 문구가 바뀌는 문제를 피한다.
- 행 전체는 최소 44px 터치 영역을 지닌 버튼이다.

### 새 채팅

- `+`를 누르면 기존 시작 가이드와 입력창이 있는 빈 채팅방을 연다.
- 사용자가 첫 질문을 보내기 전에는 세션을 저장하지 않는다.
- 첫 질문 성공 응답에서 받은 기존 `conversationId`를 활성 세션 ID로 보관한다.
- 빈 채팅방을 열었다 나간 경우 목록에 빈 세션이 생기지 않는다.

### 선택·삭제

- 헤더의 `선택`을 누르면 선택 모드로 전환한다.
- 선택 모드에서는 각 행에 체크박스를 표시하고, 모바일 탭과 마우스 클릭 모두 행 선택으로 처리한다.
- 하단 고정 버튼에 `N개 삭제`를 표시한다.
- 삭제 전 확인 다이얼로그를 사용한다.
- 목업 저장소에서는 삭제 표시 후 목록에서 제외한다. 나중에 실 API가 연결되면 백엔드의 소프트 삭제 결과를 반영한다.
- 길게 누르기는 발견성과 마우스 호환성이 낮으므로 이번 범위에서 제외한다. 추후 선택 모드 진입의 보조 동작으로만 추가할 수 있다.

## 프론트 모듈 경계

### `entities/chat`

화면이 목업 저장 방식이나 향후 HTTP 경로를 알지 못하게 다음 기능 경계를 제공한다.

- 세션 목록 조회
- 특정 세션의 메시지 조회
- 질문 전송
- 여러 세션 삭제
- 목업 데이터 초기화 또는 시나리오 구성용 테스트 도우미

세션 목록과 메시지 타입을 추가한다. 실제 엔드포인트 경로는 확정하지 않고, 이번 구현에서는 목업 저장소를 사용한다. 기존 `sendChat()`의 실 API 분기는 변경하지 않는다.

### `ChatSessionContext`

- `activeSessionId: number | null`
- 활성 세션 선택
- 새 채팅 시작 시 활성 세션 비우기
- 삭제된 세션이 활성 세션이면 활성값 비우기

메시지 배열은 Context에 저장하지 않는다. 채팅방에 들어갈 때 `entities/chat`을 통해 다시 읽어 서버 원본 방식과 동일하게 동작시킨다.

### `pages/chat`

- 진입 판정과 화면 전환을 담당하는 `ChatPage`
- 세션 목록 UI
- 기존 채팅방 UI
- 기존 `ChatStartGuide`, `SourceList` 재사용

목록과 채팅방은 같은 `/chat` 안의 명시적 화면 상태로 분리한다. 복잡해지면 별도 컴포넌트 파일로 나누되 데이터 접근은 `entities/chat` 함수만 사용한다.

## 메시지 전송 흐름

```text
첫 질문
→ 화면에 사용자 메시지 낙관적 표시
→ sendChat({ conversationId: null, ... })
→ 응답의 conversationId를 활성 세션으로 저장
→ 목업 세션·사용자 메시지·답변 저장
→ 답변 표시

기존 세션 질문
→ sendChat({ conversationId, ... })
→ 같은 세션에 사용자 메시지·답변 저장
→ lastMessageAt 갱신
```

다른 탭에 갔다 돌아올 때는 활성 세션 ID로 메시지를 다시 조회한다. 화면 로컬 배열을 복원 수단으로 사용하지 않는다.

## 로딩·오류

- 세션 목록 조회 중: 목록 스켈레톤
- 목록 조회 실패: 화면 안 로드 실패 카드와 다시 시도
- 메시지 조회 중: 대화 영역 스켈레톤
- 메시지 조회 실패: 화면 안 로드 실패 카드와 목록으로 돌아가기
- 질문 전송 실패: 현재 토스트 동작을 유지하고 사용자 질문은 재시도할 수 있게 표시한다.
- 삭제 실패: 선택 모드를 유지하고 ErrorDialog를 표시한다.
- 활성 세션이 목록에서 사라졌거나 조회되지 않으면 활성값을 비우고 목록으로 복귀한다.

## 접근성

- `+`는 아이콘만 두더라도 `aria-label="새 채팅"`을 제공한다.
- 선택 모드는 `aria-pressed` 또는 체크박스 상태를 노출한다.
- 선택 버튼, 행, 삭제 버튼은 최소 44px 터치 영역을 유지한다.
- 긴 누르기에만 의존하는 기능을 만들지 않는다.
- 삭제 확인 다이얼로그는 키보드 포커스를 가둔다.

## 검증

1. 세션이 없으면 `/chat`에서 시작 가이드와 입력창이 바로 보인다.
2. 첫 질문을 보내면 세션이 생기고 빈 세션은 생성되지 않는다.
3. 채팅 중 홈 탭으로 갔다 챗봇 탭으로 돌아오면 같은 세션 메시지가 보인다.
4. 새로고침하면 저장 세션이 있을 때 최신순 목록이 보인다.
5. 목록 제목은 첫 사용자 메시지, 보조 문구는 마지막 메시지다.
6. `+`로 새 채팅을 시작할 수 있다.
7. `선택` 모드에서 마우스 클릭과 모바일 탭으로 여러 행을 선택할 수 있다.
8. 삭제 취소 시 목록이 유지되고, 삭제 확인 시 선택한 행만 사라진다.
9. 활성 세션을 삭제하면 빈 활성값으로 목록 또는 새 채팅 상태가 된다.
10. 기존 시작 가이드, 자주 묻는 질문 즉시 전송, 출처 표시가 유지된다.
11. `pnpm typecheck`, `pnpm build`, 관련 Playwright 테스트가 통과한다.
12. 375px 폭에서 목록, 선택 하단 버튼, 채팅 입력창이 겹치지 않는다.

## 향후 실 API 연결 지점

실 API가 확정되면 `entities/chat` 내부의 목록 조회, 메시지 조회, 삭제 구현만 HTTP 요청으로 교체한다. `ChatPage`, 목록 UI, Context, 화면 상태 규칙은 변경하지 않는 것을 목표로 한다. 프론트 타입의 필드명은 백엔드 DTO가 확정될 때 어댑터에서 변환하고, 이번 작업에서 ERD나 백엔드 계약을 선행 확정하지 않는다.
