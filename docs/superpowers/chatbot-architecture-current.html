실제 요청 흐름

큰 화살표는 요청의 순서입니다. 아래 세 갈래는 같은 근거 묶음에 합쳐진 뒤에만 답변 초안으로 들어갑니다.

SSE의 범위: /api/v1/chat/stream은 “질문 확인 중 → 근거 검색 중 → 답변 정리 중 → 안전 확인 중” 같은 고정 진행 상태만 보냅니다. LLM 원문이나 안전성 검사 전 답변은 보내지 않고, 검증이 끝난 최종 답변만 complete 이벤트로 전달합니다.

단계별로 무엇이 일어나는가

  1. 세션을 열고, 같은 요청은 재사용합니다 MYSQL

    ChatApplicationService가 로그인 사용자의 세션 소유권과 request_id를 확인합니다. 동일 요청이 이미 완료됐다면 이전 답변과 출처를 재사용합니다. 새 요청이면 사용자 메시지와 처리 예정인 보조 메시지를 저장하고, 이전 대화는 최대 길이 안에서 머리·꼬리 중심으로 축약해 Core에 전달합니다.

  2. 사용자 표현을 먼저 안전하게 해석합니다 RULE / REGEX

    RuleBasedMedicationQuestionResolver가 정규식으로 토큰을 자르고 조사·공백·유니코드를 정규화합니다. 제품·성분·영양제 카탈로그와 현재 복용 이름을 합쳐 exact match를 먼저 확인합니다. 실패할 때만 길이·bigram으로 후보를 좁힌 뒤 제한된 edit distance를 계산합니다. 한 후보만 충분히 가까우면 “타이래놀 → 타이레놀”처럼 자동 교정하고, 여러 후보면 재질문합니다. 인사나 서비스 범위 밖 질문은 여기서 LLM 없이 종료합니다.

  3. 의도와 검색 계획을 규칙으로 만듭니다 RULE / REGEX + LCEL

    MedicationKnowledgeQueryBuilder는 “효능·왜 먹어”를 FUNCTION, “복용법·용량”을 DAILY_INTAKE, “주의·부작용”을 CAUTION, “같이 먹어·상호작용”을 INTERACTION으로 판정합니다. 엔터티 정규화는 제품 형태 정규식, 음식 목록, 영양제 카탈로그, 별칭을 사용하며, 두 대상이 있으면 약-약·약-영양제·약-음식·영양제-영양제의 pair key를 만듭니다. 이 단계는 LCEL RunnableLambda 체인이지만 LLM CoT나 외부 모델 호출은 아닙니다.

  4. 승인 규칙과 정확 제품 정보를 MySQL에서 찾습니다 MYSQL

    현재 복용 약·영양제, 정확 제품의 효능·사용법·주의사항, APPROVED 상태의 상호작용 규칙을 조회합니다. 상호작용 규칙은 문장 유사도가 아니라 정규화된 pair key로 판정합니다. 따라서 규칙이 없다는 결과는 “안전”이 아니라 “승인된 규칙을 찾지 못함”입니다.

  5. 공공·연구 근거를 Qdrant에서 회수합니다 RAG

    확장 질의와 대체 질의를 OpenAI 임베딩으로 벡터화합니다. 검색은 메타데이터가 있는 경우 정확한 상호작용 pair → 현재 복용 엔터티 → 넓은 의미 검색의 순서로 시도합니다. 컬렉션·환경 설정에 따라 Dense만 쓰거나, Dense 후보와 다국어 BM25 후보를 Qdrant RRF로 결합합니다. 이 단계가 RAG입니다.

  6. 검색 결과를 규칙으로 걸러 다시 정렬합니다 RULE BASED SCORE BOOST

    LLM reranker나 cross-encoder는 현재 사용하지 않습니다. 대신 쌍 일치·엔터티 일치·같은 문장 내 쌍 등장·요청 섹션·문서 유형·상호작용 유형에 정해진 보정값을 더합니다. 최소 유사도 아래라도 엔터티·섹션·관계가 모두 맞을 때만 제한된 margin 안에서 수용합니다. 같은 문서의 과도한 중복은 최대 2청크로 제한하고, 요청한 섹션을 먼저 한 개씩 고른 뒤 나머지를 채웁니다.

  7. 근거에서만 결정론적 초안을 조립합니다 DETERMINISTIC ASSEMBLY

    MedicationAnswerAssembler는 사용자 확정 복약정보, 승인 규칙, 제품 가이드, 선정된 RAG 청크를 순서대로 묶습니다. 근거가 없는 효능·사용법·주의사항·상호작용은 만들지 않고 “현재 근거에서 확인하지 못함”으로 남깁니다. 정확 제품 가이드가 있으면 일반 약물백과의 제품별 주장을 제외해 더 강한 근거를 우선합니다.

  8. LLM이 초안을 한국어로 정리합니다 LLM + STRUCTURED OUTPUT

    OpenAIMedicationAnswerGenerator는 Markdown 프롬프트 v3의 페르소나와 6요소 지침을 사용해, 초안에 있는 사실만 간결한 한국어로 재작성합니다. ChatOpenAI.with_structured_output(..., method="json_schema")로 answer와 사용한 section_types를 받습니다. 새 용량·새 안전 단정·초안 밖 항목이 생기면 LLM 답변을 버리고 결정론적 초안으로 fallback합니다.

  9. 생성 결과를 한 번 더 안전성 검사합니다 REGEX SAFETY

    RuleBasedGroundedClaimValidator가 공백을 정규화한 뒤 정규식으로 복용 시작·중단·증량·감량 지시, 진단 단정, 치료 결정 문구를 검사합니다. 하나라도 맞으면 원문을 노출하지 않고 차단 안내로 교체합니다. 면책 문구가 빠지면 추가하고 RESTRICTED로 표시합니다.

  10. 검증된 응답·출처·관측값만 저장하고 반환합니다 MYSQL + LANGSMITH

    최종 답변과 출처, 소요 시간, LangSmith trace ID를 메시지에 저장합니다. Trace에는 질문 해석, 규칙 조회, RAG 후보·선정, 초안, LLM 재작성, 안전성 검사 단계가 span으로 남습니다. 내용 수집 설정이 꺼져 있으면 질문과 답변 본문 대신 길이·해시·개수 중심의 관측값을 기록합니다.

같아 보이지만 다른 네 가지 검색·판정

구분입력현재 구현답변에서의 의미
정규식·카탈로그 해석사용자가 쓴 이름·표현토큰화, 조사 제거, 별칭, 제품 형태, 음식 접미사, 공백 결합, 후보 축소 후 edit distance무엇을 검색할지 정확히 만든다. “타이레놀”은 통칭·제품·성분 후보를 함께 가질 수 있다.
MySQL 규칙·가이드 조회정규화된 이름, pair key, 사용자 ID활성 복용 목록, 제품 가이드, APPROVED 상호작용 규칙정확한 제품 정보와 승인된 조합 경고를 결정론적으로 제공한다.
RAG / Qdrant확장 질의, 임베딩 벡터, 메타데이터 필터Dense 또는 Dense+BM25 RRF 후보 회수, 단계적 필터, 점수 보정·다양성 선택제품 테이블에 없는 공공·연구 근거의 추가 설명을 얻는다.
LLM 재작성결정론적 초안, 실제 출처 제목, 축약 대화 이력JSON schema 출력, 프롬프트 제약, 초안 대비 용량·안전 주장 검사새 사실을 찾거나 판단하지 않는다. 읽기 쉬운 한국어 답변으로 표현만 정리한다.

현재 검색의 구체적인 구성

후보 회수: 단계적 검색

질문이 “와파린과 비타민 K”처럼 쌍을 명확히 말하면 먼저 metadata.interaction_pair_keys 필터를 사용합니다. 다음으로 사용자 복용 이름의 drug_names·ingredient_names 필터를 시도하고, 충분한 후보나 섹션 커버리지가 없을 때만 넓은 semantic 검색으로 갑니다.

각 질의의 임베딩과 Qdrant 호출은 asyncio.gather로 병렬화하지만, 전체 챗봇은 “해석 → 근거 수집 → 초안 → LLM → 안전성 검사” 순서를 유지합니다.

후보 선택: 하드코딩된 점수 보정

현재의 score boost는 재현 가능한 규칙입니다. 정확 엔터티, 포함 엔터티, 두 대상 쌍, 같은 문장 관계, 요청한 섹션, 요청 문서 유형, 상호작용 유형에 보너스를 줍니다. 이는 cross-encoder가 질문과 청크를 새로 이해해 점수를 내리는 reranker와 다릅니다.

따라서 현재는 “규칙 기반 재정렬”까지 구현되어 있고, ML reranker나 LangGraph 반복 검색은 아직 실행 경로에 없습니다.

거리 방식도 설정입니다. 기본 Config는 DENSE + COSINE이지만, 환경 설정으로 Hybrid/BM25와 DOT을 선택할 수 있습니다. DOT을 쓰는 경우 임베딩 Provider가 문서·질의 벡터를 L2 정규화하고 Qdrant는 내적으로 검색합니다. 어느 방식을 쓰는지는 실행 환경의 KNOWLEDGE_SEARCH_MODE, KNOWLEDGE_VECTOR_DISTANCE에 의해 결정됩니다.

답변이 생성되지 않는 정상적인 경우

EARLY RETURN

범위 밖·인사

약·영양제·상호작용과 관련 없는 질문이나 인사는 규칙 기반으로 감지해 LLM과 RAG를 호출하지 않습니다.

CLARIFICATION

이름 또는 성분군이 모호함

후보가 여러 개이거나 “비타민 B”처럼 세부 성분에 따라 주의사항이 달라지는 경우는 하나로 단정하지 않고 후보를 제시해 다시 묻습니다.

RESTRICTED

근거가 없음

서비스 범위 안의 질문이라도 승인 규칙·제품 가이드·RAG 근거가 모두 없으면 “안전하다”라고 말하지 않고 근거가 없음을 안내합니다.

BLOCKED

안전성 검사 실패

LLM 정리문이 복용 변경 지시나 진단·치료 결정을 포함하면 그 답변 전체를 차단 안내로 교체합니다.

Check yourself

  1. “타이래놀 주의사항”에서 오타가 교정되는 단계와, 효능·주의사항이 답변에 쓰이는 근거 단계는 각각 무엇인가?
  2. Qdrant에서 청크가 검색됐더라도 답변에 바로 들어가지 않는 이유는 무엇인가?
  3. 현재 LCEL을 사용한다는 사실이 질문 의도 분류에 LLM CoT를 쓴다는 뜻이 아닌 이유는 무엇인가?

Answers

  1. 오타 교정은 규칙 기반 Question Resolver의 카탈로그·bigram·edit distance 처리다. 내용 근거는 제품 가이드(MySQL)와 RAG(Qdrant)에서 회수한다. 둘을 혼동하면 LLM이 오타를 알아서 고친다고 오해하게 된다.
  2. 검색 후보는 pair·엔터티·최소 점수·요청 섹션 조건을 통과해야 하고, 중복 제한과 다양성 선택도 거친다. 검색됨은 답변 근거로 승인됐다는 뜻이 아니다.
  3. 현재 Query Plan Chain의 LCEL 노드는 RunnableLambda로 입력 검증과 규칙 기반 Builder를 연결한다. 외부 Chat Model은 최종 답변 재작성에서만 호출된다.
