최신 약·영양제 챗봇 아키텍처

이 챗봇은 질문을 곧바로 “답변 LLM”에 넘기지 않습니다. 먼저 사용자가 무엇을 묻는지, 실제로 확인된 약·성분이 무엇인지, 위험한 요청인지 판단합니다. 그 다음에만 MySQL의 확정 정보와 Qdrant 근거를 모아 초안을 만들고, LLM은 그 초안의 사실을 짧고 읽기 쉬운 한국어로 정리합니다.

RULE

표현과 위험 판단

오타·별칭·의도·용량 변경·긴급 신호를 재현 가능한 규칙으로 판단합니다.

MYSQL

확정된 사용자·제품 정보

활성 복약정보, 제품 가이드, 승인된 상호작용 규칙, 진료 일정을 찾습니다.

RAG

공공·연구 근거 회수

OpenAI 임베딩과 Qdrant에서 작은 근거 청크를 검색하고 문맥을 붙입니다.

LLM

제한된 구조화 해석·표현

모호한 일부 질문, 일반 대화, 최종 문장 다듬기에서만 JSON 형식으로 사용합니다.

SAFETY

의료 지시 차단

복용 시작·중단·증량과 진단·치료 결정을 최종 출력 직전에 차단합니다.

실제 요청 흐름

두 갈래가 있습니다. 약·영양제 대상이 확인되면 근거 기반 RAG 경로로, 대상이 없는 일반 대화는 대화 게이트 경로로 들어갑니다. 두 갈래 모두 검증된 최종 답변만 반환합니다.

중요한 경계: 이 구조는 LangGraph가 아닙니다. AnswerMedicationQuestionUseCase가 순서를 직접 제어하는 Python UseCase입니다. 분기·재검색·LLM 호출은 관측 가능한 함수와 trace span으로 구성되어 있고, 장기 상태 저장이나 사람 승인 재개가 필요한 Graph 워크플로는 아직 도입하지 않았습니다.

단계별 구현: 질문 하나가 어떻게 움직이는가

  1. 활성 복약정보와 세션 참조를 먼저 읽습니다 MYSQL

    요청 사용자와 care episode를 기준으로 활성 약·영양제를 읽습니다. 이어 ChatSessionReferenceMemory가 같은 세션의 최근 확정 대상을 해석합니다. 예를 들어 “타이레놀은 어디에 좋아?” 다음의 “그 약 복용법도 알려줘”는 검색 전에 “타이레놀 복용법”으로 보정되며, 실제 이름은 답변 첫 안내에도 보존합니다.

  2. 규칙 기반 Resolver가 질문의 대상을 확정합니다 RULE / CATALOG

    RuleBasedMedicationQuestionResolver는 유니코드·공백·조사를 정리하고 제품·성분·음식·등록 복약정보 카탈로그에서 exact 후보를 찾습니다. 필요한 경우 후보를 좁힌 뒤 edit distance로 오타를 보정합니다. “타이래놀 효능”은 자동 보정될 수 있지만, 후보가 여러 개면 임의 제품을 고르지 않고 재질문으로 끝냅니다.

  3. 빠른 규칙 계획을 만듭니다 LCEL RunnableLambda

    MedicationQueryPlanChain은 LLM 체인이 아닙니다. RunnableLambda로 입력 검증과 MedicationKnowledgeQueryBuilder를 연결합니다. “효능”은 FUNCTION, “복용법·섭취량”은 DAILY_INTAKE, “주의”는 CAUTION, “같이 먹어도 돼?”는 INTERACTION 섹션으로 바꾸고, 두 엔터티가 있으면 약-약·약-영양제·영양제-영양제·약-음식 pair key를 만듭니다.

  4. 애매한 질문만 의미 라우터와 조건부 LLM으로 보정합니다 LOCAL SEMANTIC + LLM

    확정되지 않은 저신뢰도 질문에서만 LocalSemanticQuestionRouter가 로컬 SentenceTransformer 임베딩과 다섯 route prototype의 cosine score·margin을 비교합니다. 이 단계는 네트워크 LLM 호출이 아닙니다. 그래도 낮은 신뢰도·복수 엔터티·세션 참조가 남고 체인이 설정된 경우에만 ConditionalQuestionInterpretationChain이 후보 키와 요청 섹션을 JSON으로 고릅니다. 후보 목록 밖의 성분이나 제품을 생성할 수 없고, 숨겨진 CoT를 저장하지 않습니다.

  5. 대상이 없는 말은 대화 게이트로 안전하게 처리합니다 CONVERSATION GATE

    “안녕”, “배가 아파”, “다음 진료 일정 알려줘”처럼 제품·성분이 없는 말은 ConversationGateChain으로 갑니다. 최근 동일 세션 이력 최대 4개만 함께 전달하는 구조화 LLM 분류입니다. 민감 요청은 ConversationSafetyPolicy가 차단하고, 긴급 신호는 규칙으로 즉시 도움 요청 경로로 보냅니다. 구체 증상은 원인 진단이나 약 추천을 하지 않고, 추가로 먹으려는 제품명과 현재 약의 상호작용을 확인하도록 질문합니다. 진료 일정은 RAG가 아니라 FollowUpScheduleProvider로 조회합니다.

  6. 개인 복약정보를 질문이 요구할 때만 검색 대상으로 확장합니다 ACTIVE INTAKE

    “내가 복용 중인 약”, “등록한 영양제”, “그중 혈액 응고와 관련된 약”처럼 개인 맥락을 명시한 질문만 활성 약·영양제를 엔터티·pair key로 보완합니다. 치료군 질의는 등록 약 중 해당 치료군만 고릅니다. 일반 영양제 질문에 사용자의 리바록사반 같은 무관한 약이 섞이지 않도록, 답변 초안과 LLM 입력에도 route별로 필요한 문맥만 전달합니다.

  7. 승인 규칙과 정확 제품 안내를 먼저 확인합니다 MYSQL

    interaction_rules는 review_status = APPROVED 규칙만 pair key로 조회합니다. 제품명이 명확한 약-음식 질문은 medication_product_guides의 공식 안내를 우선 찾습니다. 규칙이 없다는 것은 병용이 안전하다는 뜻이 아니라, 현재 승인 규칙이 없다는 사실로만 다룹니다.

  8. Qdrant에서 넓게 찾되, 조건을 좁혀 근거만 남깁니다 RAG + RunnableParallel

    MedicationKnowledgeCandidateRetriever는 확장 질의와 alternate query의 임베딩을 RunnableParallel로 병렬 생성합니다. 각 검색 tier에서도 질의별 Qdrant 호출을 병렬 실행합니다. 순서는 exact pair filter → entity filter → semantic search입니다. 후보는 점수만으로 채택되지 않습니다. 엔터티·pair·요청 섹션 일치와 문서 유형을 확인하고, 규칙 기반 보정과 다양성 선택을 거칩니다.

  9. 작게 찾고, 같은 절의 큰 문맥만 붙입니다 SMALL-TO-BIG

    선정된 작은 청크에는 ParentContextResolver가 같은 문서·같은 절·같은 테이블 그룹·같은 엔터티를 가진 인접 청크만 최대 2개 더 붙입니다. 그래서 검색 recall은 작은 청크의 장점을 유지하면서도, 답변은 절의 앞뒤 문맥까지 읽을 수 있습니다. 다른 성분이나 다른 절의 이웃 청크는 붙이지 않습니다.

  10. 요청한 정보가 부족할 때만 한 번 더 찾습니다 COVERAGE RETRY

    MedicationEvidenceCoverageEvaluator가 효능·복용법·주의사항·상호작용 중 무엇이 근거로 채워졌는지 확인합니다. 부족분이 있고 RAG가 정상일 때만 CoverageGapQueryExpander가 만든 보완 질의로 최대 1회 재검색합니다. 모든 질문에 HyDE·Sub-query·무한 재시도를 적용하지 않아 지연과 잘못된 확장을 제한합니다.

  11. 근거 묶음으로 초안을 만들고 LLM은 표현만 정리합니다 DRAFT → LLM

    MedicationAnswerAssembler는 제품 가이드, 승인 규칙, 선택 청크, 근거 커버리지와 미확인 조합을 먼저 결정론적으로 조립합니다. 복약정보는 약 이름만 표시합니다. 그 후 OpenAIMedicationAnswerGenerator가 제한된 Markdown과 JSON Schema로 간결한 한국어를 만듭니다. 초안에 없던 용량·새로운 의학적 사실·지원하지 않는 섹션을 추가하면 generator는 초안 fallback을 선택합니다.

  12. 마지막 안전성 검사와 관측을 거칩니다 GROUNDING VALIDATOR

    RuleBasedGroundedClaimValidator가 생성문에서 복용 시작·중단·증량·감량 지시, 진단 단정, 치료 결정 문구를 검사합니다. 공식 제품 경고문과 일치하는 경우만 예외로 허용하며, 나머지는 차단 답변으로 교체합니다. LangSmith에는 question.resolve, query.plan, rag.retrieve, answer.draft, llm.generate, safety.validate 등의 span과 해시·건수·경로가 남습니다.

세 가지 예시로 따라가기

예시 1 · 오타가 있는 약 질문

“타이래놀 효능과 주의사항”

Resolver가 통칭·카탈로그 후보를 확인해 단일 후보면 “타이레놀”로 보정합니다. Query Plan은 FUNCTION과 CAUTION을 요청하고, MySQL 제품 가이드와 Qdrant 근거를 모읍니다. 초안에는 요청한 두 섹션만 남고, LLM은 새 용량이나 전체 부작용 목록을 덧붙이지 않습니다.

예시 2 · 영양제 조합

“마그네슘과 아연 같이 먹어도 돼?”

두 성분이 확인되면 영양제-영양제 pair key를 만들고 exact pair → entity → semantic 순으로 찾습니다. 승인 규칙·직접 근거가 있으면 상호작용을 표시합니다. 없으면 “확인하지 못한 조합”을 한 번만 표시합니다. 저위험 영양제 조합이고 위험 정책이 허용할 때만 일반 참고 안내를 제한적으로 제공하며, 개인별 안전을 단정하지 않습니다.

예시 3 · 증상만 말함

“배가 아프고 속이 쓰려”

제품명이 없으므로 RAG로 복통약을 추천하지 않습니다. Conversation Gate가 구체 증상으로 분류하면 Response Generator는 친절하게 필요한 정보를 묻습니다. “추가로 먹으려는 약의 제품명 또는 성분명”을 받으면 그때 현재 복용 약과의 상호작용 질문으로 근거 기반 경로에 들어갑니다.

예시 4 · 등록 정보 질문

“내 다음 진료 일정 알려줘”

엔터티 없는 질문이지만 Conversation Gate가 FOLLOW_UP_SCHEDULE로 분류하면 FollowUpScheduleProvider가 사용자별 다음 진료 일정을 MySQL에서 읽어 답합니다. 의료 정보 RAG와 제품 검색은 실행하지 않습니다.

현재의 의도적인 한계

아직 하지 않는 것

  • 모든 질문에 LLM CoT, HyDE, Sub-query를 실행하지 않습니다.
  • cross-encoder 또는 LLM reranker를 런타임 검색 경로에 넣지 않았습니다. 현재는 규칙 기반 점수 보정입니다.
  • 세션 밖의 장기 기억을 답변 근거로 사용하지 않습니다.
  • LLM이 새 제품명·성분명·용량을 자유롭게 만들어 검색하거나 추천하게 하지 않습니다.

앞으로 Graph가 의미 있어지는 지점

현재 선형 UseCase는 “질문 1회 → 답변 1회”에 적합합니다. 다만 영양제 등록에서 성분 중복 → 총량 계산 → 승인 규칙 → 부작용 DB → 위험도 → 사용자 추가 정보 → 사람 승인 → 재개처럼 상태를 오래 보존하고 되돌아와야 하는 흐름이 확정되면, 그 기능에만 LangGraph 같은 상태 그래프를 도입할 근거가 생깁니다.

  3. “배가 아파”가 들어왔을 때, 챗봇이 곧바로 위장약을 추천하지 않는 이유와 다음 행동은 무엇인가?

Answers

  1. 같은 성분이 따로 언급된 문서를 단순 유사도만으로 상호작용 근거처럼 쓰지 않기 위해서다. exact pair가 없을 때만 entity와 넓은 의미 검색으로 확장한다.
  2. Semantic Router는 route 제안만 하고 제품·성분·검색 섹션을 만들지 못한다. 조건부 LLM도 서버가 준 candidate key 밖의 새 엔터티를 만들지 못하며, JSON 결과를 다시 검증받는다.
  3. 증상만으로는 원인·치료를 판단할 수 없기 때문이다. Conversation Gate는 증상 확인 대화로 전환해, 추가 복용하려는 제품명 또는 성분명을 물은 뒤 현재 복약정보와의 상호작용만 근거 기반으로 확인한다.
