# #303 챌린지 마이그레이션

## 변경 범위

- `ChallengeParticipationStatus.EXPIRED` 추가: 종료된 미달성 참여를 표현하는 값만 추가한다. 만료 자동 전환 로직은 이 작업에 포함하지 않는다.
- `ChallengeVerification`의 참여 ID + 인증 날짜에 유니크 제약을 추가한다.
- 기존 마이그레이션은 수정하지 않고 `37_20260908090000_challenge_daily_verification.py`를 추가한다.
- 기존 상태 컬럼은 `VARCHAR(9)`이므로 EXPIRED 저장을 위한 컬럼 변경은 필요 없다.
- API 연결, 인증 중복 요청의 사용자 안내, 챌린지 등록 및 초기 데이터 변경은 포함하지 않는다.

## 데이터 보존 및 주의사항

- 마이그레이션이 기존 중복을 발견하면 명시적으로 중단한다. 인증을 자동 삭제하거나 합치지 않는다.
- 사전 검사 후 중복 요청이 들어오더라도 단일 ALTER TABLE 문이 실패하면서 기존 일반 인덱스를 보존한다(MySQL 8.0 검증).
- 적용 중에는 챌린지 인증 쓰기를 일시 중단하는 것을 권장한다.
- 현재 정책은 하루 최대 한 번 인증이다. 하루 여러 번 인증을 도입할 때는 이 제약을 재검토해야 한다.
- 다운그레이드는 일반 인덱스를 복구하고 데이터를 유지한다. EXPIRED 값을 삭제하거나 ACTIVE로 바꾸지 않는다. EXPIRED를 모르는 이전 애플리케이션으로 되돌릴 때는 해당 상태의 처리 방안을 먼저 결정해야 한다.
- 기존 API는 다른 idempotency_key를 사용한 같은 날짜의 중복 요청을 별도 응답으로 처리하지 않는다. DB 중복은 차단되지만 사용자에게 적절한 응답을 반환하는 처리는 #304 연결 전 백엔드와 협의해야 한다.

## 적용 전 확인

WSL에서 프로젝트 루트로 이동한다. `.venv`는 WSL Python 환경이며 npm은 사용하지 않는다.

```bash
cd /mnt/c/dev/AH_05_05
DB_HOST=127.0.0.1 DB_PORT=3307 .venv/bin/aerich heads
```

3307은 2026-09-08에 확인한 이 로컬 Docker MySQL의 공개 포트다. 다른 환경에서는 해당 환경의 실제 포트를 확인한다. 사용자와 비밀번호는 기존 환경설정을 사용한다.

목록이 이번 변경 37번만인지 먼저 확인한다. 다른 대기 항목이 있으면 함께 적용될 변경을 검토한 뒤 진행한다. 중복 조회는 챌린지 테이블이 존재할 때 수행한다.

```sql
SELECT user_challenge_id, verification_date, COUNT(*) AS duplicate_count
FROM challenge_verifications
GROUP BY user_challenge_id, verification_date
HAVING COUNT(*) > 1;
```

검토와 백업을 마친 적용 환경에서만 실행한다.

```bash
DB_HOST=127.0.0.1 DB_PORT=3307 .venv/bin/aerich upgrade
```

DB 초기화, 볼륨 삭제, `init-db`는 필요하지 않다. 이미 적용된 버전은 Aerich가 건너뛴다.

## 2026-09-08 검증 결과

- WSL + 별도 MySQL 8.0 테스트 컨테이너에서 검증했다. 사용자 DB를 테스트 DB로 사용하지 않았다.
- 모델·마이그레이션·기간 계산 테스트: 21개 통과.
- 기존 챌린지 API 테스트: 5개 통과.
- 검증한 동작: 같은 날 다른 요청 키 차단, 다음 날/다른 참여 허용, 기존 중복 발견 시 무변경 중단, 사전 검사 이후 중복 삽입 시 인덱스 보존, downgrade 데이터 보존.
- 실제 로컬 MySQL 컨테이너는 중지 상태에서 시작했으며, 데이터 및 볼륨은 초기화하지 않았다.
- 실제 로컬 DB 적용은 보류했다. `aerich heads`에 이번 버전 외에도 31번 이메일 인증부터 시작하는 총 9개 항목이 대기 중이어서 임의로 일괄 적용하지 않았다.
