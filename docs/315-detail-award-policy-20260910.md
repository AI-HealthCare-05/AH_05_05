# 맞춤 챌린지 상세 진입 지급 정책

## 승인된 동작

- 하루 완료가 아니라 챌린지 전체의 실제 목표를 모두 완료해야 한다. 목표0건은 달성이 아니다.
- 전체 완료 후 해당 챌린지 상세를 열면 서버에 지급 확인을 요청한다. 홈·목록·배지 목록 조회만으로 배지를 지급하지 않는다.
- 서버는 같은 사용자/참여 잠금 아래 현재 복용 기록을 다시 확인한다. 진행 중 기록을 되돌려100%가 아니면 지급하지 않고 최신 진행 상태를 반환한다.
- 조기 달성 확정 후에는 원본 복용 기록을 수정해도 확정 결과·배지가 유지된다. 기존 종료/취소 스냅샷과 이미 지급된 배지도 보존한다.
- 전용 워커는 사용하지 않는다. 목록·상세·배지 조회 및 복용 기록 변경 API가 기간이 지난 참여의 결과를 확정하되 새 배지는 만들지 않는다. 종료 후 미수령 달성 배지는 해당 상세를 열 때 수령한다.
- 재진입·중복 요청은 같은 지급 건을 반환한다. 실제 신규 지급 응답에만 획득 팝업을 연결한다.
- 지급 실패는 다시 시도할 수 있다. 사용자가 다른 화면이나 계정으로 이동한 뒤 도착한 응답은 팝업이나 현재 화면을 변경하지 않는다.

## API

`POST /api/v1/user/custom-challenge-participations/{participation_id}/claim-reward`

요청 본문 없음. 응답은 `participation`, `award`(없으면 null), `newlyAwarded`다. 서버가 최신 상태를 확인하고 판정하므로 프런트엔드의 100% 표시는 권한이나 지급 근거가 아니다. 판정과 응답 생성 모두 동일한 사용자 잠금과 트랜잭션 안에서 처리한다.

## 검수 순서

1. 오늘1일짜리 새 복약 챌린지에 참여한 후 홈에서 마지막 목표를 완료한다.
2. 홈·챌린지 목록만 본 상태에서는 신규 배지가 지급되지 않는다.
3. 해당 상세로 들어오면 달성 확정 및 획득 팝업/배지 카드가 표시된다. 자정 대기나 종료 시간 SQL은 필요 없다.
4. 확인을 누른 뒤 재진입·새로고침해도 같은 배지가 추가 지급되지 않고 팝업도 반복되지 않는다.
5. 지급 후 홈에서 기록을 되돌려도 해당 챌린지의 확정 결과와 배지는 유지된다.
6. 다른 새 챌린지에서는 전체 완료 후 상세 진입 전에 기록을 되돌려 지급되지 않는지 확인한다.
7. 영양제도 같은 방식으로 확인한다. 일부 날짜만 완료한 상태에서는 지급되지 않는다.

## 운영 적용

DB 스키마 변경이나 기존 데이터의 종료 시간 변경은 필요 없다. 챌린지 전용 워커는 제거했다. 이전 배포에서 실행 중인 `custom-challenge-worker` 컨테이너만 중지·제거하면 된다. 다른 워커나 DB는 유지한다. 사용자가 접속하거나 관련 기록을 수정하지 않으면 저장된 상태는 다음 API 요청까지 진행 중일 수 있다.

## 검증 범위

- 기존 챌린지 UI 회귀 81개: 일수 계산, 당일 완료·되돌리기, 날짜 스크롤, 자동 갱신, 홈, 참여·취소·지난 기록.
- 분리된 실제 MySQL/JWT 통합 10개: 중복 수령, 복약·영양제 수령/되돌리기 양쪽 잠금 순서, 종료 결과 보존, 조회 시 확정·미지급.
- 신규 상세 수령과 공통 배지 연출 33개: 실제 신규 지급에만 팝업, 오류 재시도, 인증 만료, 화면 이탈, 저감 모션, 작은 화면, 중복 방지. 기존 회귀와 합쳐 UI 114개 통과.
- 워커 제거 후 격리 SQLite/API·Compose 회귀 123개와 실제 MySQL 통합 10개, Ruff 통과. 프런트엔드는 변경하지 않았으며 위 UI·TypeScript·빌드는 직전 지급 정책 구현의 검증 결과다. 기존 큰 번들 청크 경고는 남아 있다.
- 실제 사용자 DB는 조작하지 않는다. MySQL 통합 검증은 별도 3315 포트와 실행별 임시 스키마에서 수행한다.
