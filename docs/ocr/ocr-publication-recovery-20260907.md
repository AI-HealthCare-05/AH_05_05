# OCR 최종 저장 복구 및 마이그레이션 검증 정리 — 2026-09-07

## 요청 범위

엄격 감사의 **2번(최종 DB 저장 실패)**만 수정하고, 함께 실패한 마이그레이션 검증을 정리했다. 1번 잘린 약명과 3번 미래 조제일의 추출·신뢰도 로직은 변경하지 않았다.

작업 위치는 `906/AH_05_05` 로컬 복사본이다. 기존 미커밋 변경을 보존했으며 커밋·push·별도 Git 폴더 반영은 하지 않았다.

## 저장 실패 수정

- 분석·전처리 이미지 저장이 끝나면 같은 결과를 유지한 채 **DB 게시만 최대 3회** 시도한다. 재시도 대기는 0.1초·0.2초이며 OCR·LLM·이미지 저장을 다시 호출하지 않는다.
- `PROCESSING`이고 아직 확정되지 않은 작업만 조건부 갱신한다. 이미 게시된 결과나 사용자의 확정 결과를 덮어쓰지 않는다. DB 커밋은 됐지만 응답이 유실되는 경우도 이 조건으로 보호한다.
- 게시 시도가 소진되면 `FAILED / WORKER_INTERRUPTED`로 조건부 전환한다. 이 전환이 실제로 1행에 적용됐을 때만 이미지 삭제를 시도한다. 결과가 이미 게시됐거나 DB 응답이 불확실하면 파일을 삭제하지 않는다.
- DB 전체 장애로 실패 상태까지 저장하지 못하면 ARQ에 남은 실패 기록을 사용한다. 이후 상태 조회 또는 5분 주기 정리에서 함수·작업 ID·큐·실패 여부·실행 시각이 일치하는 기록만 인정하여 `PROCESSING` 상태를 정리한다. Redis 기록이 없거나 조회가 실패했다는 이유만으로 작업을 실패 처리하지 않는다.
- 실패 근거가 정리 주기 전에 사라지지 않도록 ARQ 결과 보존 시간을 리뷰 TTL+10분(기본 70분)으로 설정했다.
- 6단계 처리 기록과 `persistMs / queueWaitMs / totalMs` 계약은 유지했다.

핵심 파일: `app/services/medication_guide_ocr_jobs.py`, `app/workers/medication_guide_ocr_worker.py`.

## 마이그레이션을 정리한 방식

기존 2개 테스트는 7번·21번 마이그레이션 당시의 **전체 앱 모델**을 현재 전체 모델과 같다고 요구했다. 이후 추가된 별도 기능의 모델·필드 때문에 실패하는 비교였다.

1. 과거 7번·21번의 SQL과 `MODELS_STATE`는 수정하지 않았다. 이미 적용된 마이그레이션 이력을 현재 모델로 덮어쓰지 않았다.
2. 각 과거 단계가 책임지는 소유권/FK/유일성/NULL/필드 타입·이름을 고정된 기대값으로 검사한다. 소유권 backfill과 중복 키 정리가 제약 추가보다 먼저 실행되는 SQL 순서 검사도 추가했다.
3. 현재 저장 모델 검사는 **최신 마이그레이션**과 비교하도록 분리했다. `OcrJob`, `Medication`, `CareEpisode`의 저장 필드·관계·인덱스·유일성 계약을 검사하되, 설명문·선언 순서·역방향 ORM 관계 때문에 실패하지 않게 했다.
4. 검사 약화 여부도 확인했다. 별도 Python 프로세스에서 `stage_results`를 마이그레이션 없이 NOT NULL로 바꾸자 최신 스키마 검사가 실패했고, 원래 값으로 복원하면 다시 통과했다.

수정 테스트: `tests/models/test_async_ocr_migration.py`, `tests/models/test_ocr_v3_storage_migration.py`.

실제 로컬 DB도 읽기 전용으로 대조했다. 최신 적용 이력은 `31_20260906000000_add_care_episode_hospital_name.py`이며 OCR 관련 10개 컬럼의 타입과 NULL 허용 여부가 일치했다. 따라서 새 마이그레이션 생성이나 실제 DB DDL 변경은 하지 않았다.

## 검증

- 새 저장 장애 회귀 5개를 먼저 실행하여 모두 기존 결함으로 실패하는 것을 확인했다.
- 수정 후 저장·작업·worker·마이그레이션 관련 좁은 검사: **63 passed**.
- 전체 OCR 관련 검사(기존 감사와 같은 범위 + 새 회귀): **516 passed, 24.68초**. 기존 마이그레이션 실패 2개도 해소됐다.
- 실제 테스트 DB의 SQL 실행 경계에서 일시 실패, 재연결 실패, 커밋 응답 유실, 즉시 사용자 확정, 재시도 소진, DB 전체 장애 후 ARQ 기반 복구를 검증했다. 운영 DB 장애를 실제로 일으킨 테스트는 아니다.
- `ruff check app tests`: 통과. 수정 Python 6개 파일 format check 및 scoped `git diff --check`: 통과.
- 타입 검사에는 기존과 같은 **67개 오류(10개 파일)**가 남아 있다. 새 저장·복구 helper에서 추가 오류는 보고되지 않았지만 전체 타입 검사 통과로 표현하지 않는다.

## 품질 검토 및 실행 환경

기존 사용자 변경과 겹치는 구현 파일은 파일 전체 자동 단순화를 하지 않았다. 이번 수정 범위만 수동 검토하고 독립 읽기 전용 검토를 수행했다. 독립 검토자는 관련 테스트 16개를 별도 실행했으며 **범위 내 차단 문제 없음**으로 판정했다. 검토에서 제안한 추가 복합 장애 시나리오(커밋 응답 유실 + 이후 게시 재시도 모두 실패 + 최종 실패 전환 0행)도 기존 회귀에 추가했고, 확정 결과와 이미지 보존을 확인한 뒤 전체 516개를 재실행했다.

활성 OCR 작업 0건을 재확인하고 로컬 `ocr-worker`를 재시작했다. 시작 시각은 21:30:04 KST, 새 health 레코드는 21:30:06이며 21:30:27 검사에서 `j_ongoing=0, queued=0`으로 통과했다. 컨테이너 새 import에서 결과 보존 4,200초를 확인했다. DB 스키마 변경과 외부 OCR 호출은 하지 않았다.

## 남은 범위

- 기존 감사의 1번 잘린 약명, 3번 미래 조제일은 사용자 요청대로 미수정 상태다.
- DB 장애가 ARQ 결과 보존 기간까지 넘으면 기존 stale 만료·삭제 정책이 적용된다. 무기한 결과 복구나 전원 중단 시 분석 결과 재사용을 새로 구현한 것은 아니다.
- 정리 작업은 처리 중인 각 작업의 Redis 결과를 순서대로 조회한다. 매우 많은 작업이 동시에 고착되고 Redis도 느리면 정리 시간이 길어질 수 있으며, 대량 장애용 병렬 배치 처리는 이번 범위에 추가하지 않았다.
- 외부 OCR·LLM 재호출이나 새 실제 문서 정확도 측정은 이번 변경 검증에 필요하지 않아 실행하지 않았다.
