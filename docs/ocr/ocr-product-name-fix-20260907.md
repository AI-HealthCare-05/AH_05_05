# 제품명 대신 성분명을 선택하던 오류 수정

기준: 2026-09-07 13:36 KST 사용자 피드백과 `docs/문서 예시/복약안내/4.jpeg`.

## 문제와 원인

General OCR에는 제품명이 있었지만, 약품명/성분이 두 줄로 인쇄된 표에서 숫자 스케줄에 더 가까운 성분행이 이름으로 선택됐다. `ocr_layout.py`의 `_anchored_layout_rows` → `_name_blocks_for_row`에서 제품 제형과 성분+함량을 동등한 이름 신호로 취급한 뒤 세로 거리를 비교하기 때문이다. `medication_rows.py`는 선택된 이름 셀을 정규화해 전달하므로 잘못 선택된 성분명이 검토 화면까지 유지됐다.

실제 입력에서 제품명 중심 Y는 579.5 / 818.0 / 1054.5였고, 숫자 중심 Y는 667.5 / 888.5 / 1121.5였다. 세 제품 모두 기존 행 후보 범위 안에 있었다. 따라서 후보 범위를 넓히거나 OCR·LLM을 변경할 필요는 없었다.

## 변경과 수용 기준

- `app/services/medication_ocr_v3/pipeline/ocr_layout.py`: 기존 같은 행 후보 안에서 제형이 있는 제품명을 성분+함량 후보보다 우선한다. 후보 필터, 행 경계, 숫자 매핑, 제품 후보가 없을 때의 거리 기반 선택은 보존한다.
- `tests/ocr_v3/test_internal_pipeline.py`: 환자 정보 없는 합성 표를 사용해 제품+성분 이중행, 제조사 제외, 제품 후보 없는 행의 기존 처리, 세 숫자 필드 보존 및 기존 함량 파서 계약을 검증한다. 현실적인 블록 높이를 표현하도록 기존 `_block` 도우미에 기본값 10의 높이 인자를 추가했다.
- 기존 미커밋 편집은 보존했다. 이번 구현 변경은 이름 선택 정렬 키 1개와 설명 주석 1줄뿐이다.

## 실제 입력 재검증

같은 이미지에서 한 번 얻은 OCR 블록을 메모리에 유지하고 수정 전·후 코드를 각각 새 프로세스로 실행했다. 실제 환자 정보나 전체 OCR은 보고서·fixture에 저장하지 않았다.

| 항목 | 수정 전 이름 | 수정 후 이름 | 투약량 / 횟수 / 일수 |
| --- | --- | --- | --- |
| 1 | 클라불란산칼륨 0.125g 외 | 오메크라정625밀리그램 | 1 / 3 / 5 |
| 2 | 덱시부프로펜 0.3g | 글로덱시정300mg | 1 / 3 / 5 |
| 3 | 레바미피드 0.1g | 휴니즈레바미피드정 | 1 / 3 / 5 |

이름 셀에서 유래한 함량은 각각 `625mg`, `300mg 0.3g`, `0.1g`이다. 두 번째는 원문 제품 블록의 `300mg`와 괄호의 `0.3g`를 모두 보존하는 기존 파서 결과다. 이번 수정은 동등 단위 병합 또는 함량 표시 정책을 변경하지 않았다.

입력 SHA-256: `7ab4632061839489a5a421b4829597b3f89cd0964916287147713736128c51ae1`

## 검토 범위와 전달

- 비교 기준은 버그 수정 직전 파일 스냅샷이며, 기존 dirty tree 전체를 이 버그의 diff로 취급하지 않았다.
- 중첩된 기존 편집을 보호하기 위해 자동 단순화는 생략하고 이번 diff만 수동 검토했다.
- 독립 읽기 전용 검토에서 신규 P0/P1 문제는 없었으며, 검토자도 파이프라인 테스트 24개 통과를 확인했다.
- 남은 기존 경계: 제품명에 인식 가능한 제형(정·캡슐 등)이 없고 성분행에도 함량이 있으면, 기존 거리 기준으로 성분명을 선택할 수 있다. 이번 수정이 모든 제품명/성분명 구분을 해결했다는 의미는 아니다. 이 사진의 세 제품은 제형 표기가 있어 수정 대상에 해당한다.
- 브라우저 재업로드와 전체 16장 외부 OCR 벤치마크는 이번에 재실행하지 않았다. 문제 이미지의 동일 OCR 재처리와 관련 자동 테스트로 검증했다.
- 이미 저장된 OCR 결과는 덮어쓰지 않았다. 수정된 결과를 보려면 해당 사진을 새로 업로드해야 한다.
- 로컬 복사본 작업이며 커밋·브랜치 작업·push는 하지 않았다.
