# OCR 전처리 v3.1 변형 매트릭스

> **현재 운영 선택 (2026-09-04): `v3.1.3`**
>
> 과거 매트릭스의 안전 기본값은 `v3.1.1`이었지만, 3장 OCR·LLM 반복 검증 결과를 반영해
> 전처리 p95가 더 낮고 주요 추출 품질을 유지한 `v3.1.3`을 현재 운영값으로 전환했다.
> 아래의 과거 측정·판정 문구는 실험 이력으로 보존한다.

## 목적과 측정 범위

`OCR_PREPROCESS_VERSION`으로 선택 가능한 v3.1.0~v3.1.8의 GrabCut 프로파일을 비교한 기록이다. 기준 사진 1장은 각 변형별로 warmup 2회 후 8회 측정했으며, 표의 시간은 그 8회에서 계산했다. `계약`은 기준 출력의 mode·operations·변환·크기·JPEG hash 등 고정 전처리 계약과의 일치 여부다.

## 공통 전처리 프로세스

버전별로 전체 파이프라인을 다르게 만든 것이 아니라 문서 영역 검출 단계의 GrabCut 설정만 바꿨다. 아래 단계와 실행 순서는 모든 버전에서 같다.

| 순서 | 공통 처리 | 목적 | 버전별 변경 여부 |
| ---: | --- | --- | --- |
| 1 | JPEG·PNG 형식, 용량, 픽셀 수와 긴 변 검증 | 잘못되거나 과도하게 큰 입력 차단 | 없음 |
| 2 | EXIF 방향 반영, ICC profile 적용, sRGB 변환 | 촬영 방향과 색공간 통일 | 없음 |
| 3 | 축소 탐지 이미지에서 contour와 Hough line 후보 생성 | 문서의 외곽 사각형 탐색 | 없음 |
| 4 | 후보가 없거나 신뢰도가 부족하면 GrabCut 실행 | 문서와 촬영 배경 분리 | **반복 횟수·작업 edge·실행 임계값만 변경** |
| 5 | 후보 그룹화·안정화, 안전 확장, 원근 보정 | 기울어진 문서를 정면 형태로 변환 | 알고리즘은 같지만 4단계 결과에 따라 좌표가 달라질 수 있음 |
| 6 | 원근 결과 품질 검사와 rollback | 보정 결과가 나쁘면 crop·deskew 또는 full-frame으로 복귀 | 없음 |
| 7 | LAB illumination 보정과 가독성 지표 계산 | 조명 편차를 줄이고 글자 대비 유지 | 없음 |
| 8 | 흰색 안전 테두리, sRGB 유지, JPEG quality 95 인코딩 | CLOVA 전달 이미지와 미리보기 생성 | 없음 |

선명화 강도, 채도, 조명 보정, JPEG 설정, OCR provider, 후보 구조화와 LLM 로직은 버전별로 변경하지 않았다.

## 조정 파라미터 의미

| 파라미터 | 적용 위치 | 값을 낮췄을 때 | 주요 위험 |
| --- | --- | --- | --- |
| GrabCut 반복 횟수 | `cv2.grabCut()`의 배경·전경 마스크 refinement | 반복 연산이 줄어 빨라짐 | 복잡한 배경에서 문서 경계 정밀도 저하 가능 |
| GrabCut 작업 edge | GrabCut에 넣는 축소 이미지의 긴 변 | 처리 픽셀 수가 줄어 크게 빨라짐 | 탐지 좌표가 달라져 최종 원근 변환·크기·JPEG가 바뀔 수 있음 |
| GrabCut 실행 임계값 | contour/Hough 최고 신뢰도가 임계값보다 낮을 때 GrabCut 실행 | 임계값이 낮을수록 GrabCut을 생략하기 쉬움 | 잘못된 후보를 그대로 사용하거나 원근 보정을 생략할 수 있음 |

작업 edge는 GrabCut 탐지용 축소 이미지에만 적용된다. 최종 출력 해상도를 직접 낮추는 옵션은 아니지만, 탐지 좌표 변화가 최종 이미지에 간접적으로 영향을 줄 수 있다.

## 기본 권장값

기본값은 **v3.1.1**이다. 기준과 동일한 800 px 작업 edge·0.82 임계값을 유지하면서 GrabCut만 4회에서 3회로 줄이며, 보조 56장 모두가 기준 계약과 exact match였다. 이 매트릭스 단일 실행에서는 기준선보다 p95가 낮지 않았지만, 앞선 전용 재측정에서는 기준 대비 p95 10.65% 감소와 exact output이 확인됐다. 반대로 v3.1.7도 56/56 exact이지만 이 기준 사진에서 다른 경로를 만들지 않아 필요한 10% 개선을 입증하지 못했다.

## 전환과 확인

프로젝트 루트의 `.env`에서 원하는 값을 설정한 뒤 worker를 재시작한다. 지원값 이외의 값은 설정 검증에서 거부된다.

```powershell
# .env의 OCR_PREPROCESS_VERSION=v3.1.1 을 원하는 v3.1.x 값으로 변경
# env_file 값을 다시 주입하려면 단순 restart가 아니라 컨테이너를 재생성해야 한다.
docker compose up -d --force-recreate ocr-worker
docker compose ps ocr-worker
```

새로 제출한 작업이 `ready_for_review` 또는 `complete`가 되면 인증된 사용자로 상태를 조회한다. 이전 작업에는 전환 전 버전이 남으므로 새 작업으로 비교한다.

```http
GET /api/v1/ocr/jobs/{ocrJobId}
```

응답 예시는 다음과 같다.

```json
{
  "batchId": "b_123",
  "ocrStatus": "ready_for_review",
  "preprocessVersion": "v3.1.1",
  "preprocessElapsedMs": 1796
}
```

같은 소유자·인증 문맥에서 아래 endpoint를 브라우저나 HTTP 클라이언트로 열어 전처리 JPEG를 육안 비교한다. 응답은 private/no-store이며 JPEG hash 검증을 거친 저장본이다.

```http
GET /api/v1/ocr/jobs/{ocrJobId}/processed-image
```

## 해석 한계

이번 매트릭스는 전처리만 실행했다. OCR provider와 LLM 호출은 모두 **0회**이며 외부 호출 비용도 0이다. 따라서 이 결과는 전처리 지연·메모리·payload·출력 계약의 근거일 뿐, 약품 필드 인식 정확도, LLM 보정 품질, 전체 촬영 조건에서의 성능 개선을 보장하지 않는다. 운영 전환 시에는 실제 승인된 비식별 시험 자료로 OCR 결과와 재촬영률을 별도 관찰한다.

## REF-002 재측정과 후보 선정

`v3.1.0`, `v3.1.1`, `v3.1.2`, `v3.1.3`, `v3.1.7`은 전처리 JPEG SHA-256까지 동일했다. 즉 이 사진에서는 CLOVA에 전달될 픽셀이 같으므로 버전별 OCR 호출을 반복할 실익이 없다. `v3.1.4~v3.1.6`은 문서 전체와 글자 가독성이 육안상 보존됐지만 좌표·출력 크기·JPEG가 달라 고정 계약 후보로는 탈락한다. `v3.1.8`은 배경을 포함한 full-frame으로 바뀌고 payload도 증가해 제외한다.

전처리 결과만으로 선정한 후속 비교 후보는 다음 세 개였다.

- **v3.1.1 — 안전 기준:** 익명 보조 56장 모두 기준 출력과 동일한 현재 기본값.
- **v3.1.3 — 동일 출력 속도 후보:** REF-002에서 출력이 완전히 같고 p95가 22.00% 감소했다. 다만 보조 비교는 54/56이므로 추가 사진 검증이 필요하다.
- **v3.1.6 — 공격적 속도 후보:** REF-002에서 p95가 51.11% 감소했고 육안상 문서가 보존됐다. 좌표·크기·JPEG가 달라 실제 OCR 결과 비교를 통과해야 한다.

v3.1.2는 v3.1.3과 보조 exact 결과가 같은 54/56이면서 이 사진에서는 더 느려 우선 후보에서 제외했다. v3.1.7은 56/56 exact이지만 이 사진에서 v3.1.1과 같은 처리 경로를 사용해 측정 차이를 독립적인 최적화 효과로 보기 어렵다.

### REF-002 실제 파이프라인 확인

서로 다른 provider JPEG만 실제 CLOVA·구조화 파이프라인으로 확인했다. v3.1.0·v3.1.1·v3.1.2·v3.1.3·v3.1.7은 JPEG hash가 같으므로 가장 빠른 v3.1.3을 대표로 한 번 호출했다. 좌표가 달라진 해상도 축소 계열은 v3.1.4·v3.1.5·v3.1.6을 각각 호출했다. v3.1.8은 원근 보정이 사라진 전처리 품질 실패로 호출하지 않았다.

| 버전 | 약품 행 | low confidence | preprocess | OCR | candidate | LLM | validate | 판정 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| v3.1.3 | 7 | 4 | 1,575 ms | 2,453 ms | 106 ms | 8,141 ms | 1 ms | 속도 후보 |
| v3.1.4 | 0 | 0 | 1,392 ms | 2,911 ms | 98 ms | 0 ms | 0 ms | 탈락 |
| v3.1.5 | 7 | 5 | 1,045 ms | 2,421 ms | 107 ms | 1,375 ms | 1 ms | 신뢰도 저하로 탈락 |
| v3.1.6 | 0 | 0 | 873 ms | 2,661 ms | 96 ms | 0 ms | 0 ms | 탈락 |

v3.1.3은 조제일과 약품 7개, 각 투약량·횟수·일수를 구성했다. v3.1.5도 필드 값은 같았지만 low confidence가 4개에서 5개로 늘었다. v3.1.4와 v3.1.6은 날짜만 남고 약품 행이 만들어지지 않았다. 따라서 **REF-002의 최종 속도 후보는 v3.1.3**, 여러 촬영 조건을 고려한 **안전 기본값은 v3.1.1**이다. 실제 외부 호출은 CLOVA 4회, LLM 2회였다. 저장소 밖 산출물에는 공개 리뷰 구조와 stage 시간만 저장하고 OCR 원문은 저장하지 않았다.

## 3장 OCR·LLM 반복 검증

전처리 전용 결과가 실제 구조화 품질까지 유지하는지 확인하기 위해 2026-09-04에 `v3.1.1~v3.1.8`을 같은 3장으로 각각 3회 실행했다. 실행은 외부 호출 간 간섭을 줄이기 위해 직렬로 수행했고, 반복마다 후보 순서를 반대로 배치했다.

- 사진: 기울어진 고해상도 실사진(`real-angle`), 접힘·반사 실사진(`real-folded`), 정형 합성 문서(`synthetic-exact`)
- 정답 범위: 조제일, 병원명, 약품명, 함량, 1회 투약량, 하루 횟수, 투약일수 중 사진별로 확정 가능한 필드
- 모델: CLOVA General OCR v2 + `gpt-4o-mini`, temperature `0`
- LLM 역할: OCR 근거가 충돌한 조제일·함량의 block ID만 선택하며 약품명·투약량·횟수·일수·병원명을 생성하거나 교정하지 않음

### LLM 호출과 결과 해석

총 외부 호출은 CLOVA 72회, OpenAI 15회였다. LLM 15회는 모두 성공했고 나머지 57회는 정상 생략됐다. 이 중 12회는 전처리 손상으로 검증 가능한 약 행이 없어 `NO_EVIDENCE_ROWS`로 생략된 것이므로 속도 개선으로 간주하지 않는다. LLM은 `real-angle`의 모호한 날짜·함량 근거에서만 호출됐으며 다른 두 사진에서는 호출할 모호성이 없었다.

`v3.1.1`·`v3.1.2`·`v3.1.3`·`v3.1.7`의 전체 점수는 같지만 결과 내용까지 모두 같은 것은 아니다. `real-folded`에서 기준은 `에리텐캡슐`의 1회 투약량을 놓쳤고, `v3.1.2~v3.1.3`은 대신 `아목클정375mg`의 1회 투약량을 놓쳤다. 따라서 동률 점수만으로 완전 동일 출력을 주장하지 않는다.

### 결론

운영 기본값은 **v3.1.1을 유지**한다. 이 버전은 기존 익명 보조 56장 모두 기준 계약과 일치한다. **v3.1.3은 추가 검증할 속도 후보**로 유지한다. 이번 3장에서는 정확도·추출률·완전 행 비율을 유지하면서 전처리 p95를 13.26% 줄였지만, 기존 보조 비교가 54/56이고 접힌 사진의 누락 위치가 달라졌으므로 바로 승격하지 않는다. `v3.1.4~v3.1.6`과 `v3.1.8`은 품질 손실로 제외한다.
