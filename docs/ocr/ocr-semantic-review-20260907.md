# OCR 5항목 근거 검토 — 2026-09-07

## 변경 범위

`906/AH_05_05` 로컬 복사본에서 정확도 우선으로 구현했다. 기존 사용자 변경은 보존했으며 커밋·push·실행 중 서비스 재시작은 하지 않았다.

- LLM이 약명·함량·1회량·횟수·일수를 함께 검토하고, 각 필드의 원문 발췌·근거 ID·판단 상태를 반환한다.
- 서버가 실제 OCR 원문 일치, 행 소속, 숫자 경계, 필드 적합성과 값 범위를 검사한다. 실패·불확실·누락 응답은 기존 규칙 결과를 보존하고 확인 필요 사유를 남긴다.
- 개인정보 노출을 줄이기 위해 임의의 주변 문구를 추가하지 않는다. 기존 필터를 통과한 약물 행과 귀속 가능한 제품명·함량 근거만 사용한다.
- 제목에는 원래 약명만 표시한다. 약명 안의 함량은 유지하지만 별도 함량 필드를 제목 끝에 추가하지 않는다.
- 투약량 표시는 `1.00 → 1`, `2.00 → 2`, `1.50정 → 1.5정`으로 불필요한 소수 끝자리 0만 제거한다. 저장값과 편집 입력값은 변경하지 않는다.

## 비교 방법

`scripts/benchmark_ocr_semantic_review.py`는 문서별 CLOVA OCR을 한 번 호출하고, 메모리의 동일 OCR 객체로 no-LLM / legacy / semantic을 각각 3회 비교한다. LLM 두 방식의 실행 순서는 교대한다. 기존 보정 정답 및 평가 상태를 고정하며, 원래 정답 기준 점수도 별도로 보존한다.

16개 자료에는 재촬영 판정 2건과 중복 문서가 포함된다. 따라서 독립적인 16건의 신규 검증 집합으로 해석할 수 없다. 정답 복원, 기존 정답 훼손, 새 FP를 각각 집계하며 FP는 점수 분모와 별도다. 반복 실행은 LLM 변동을 확인하는 것이지 독립 표본 수를 늘리는 것이 아니다.

체크포인트에는 점수·판정·해시·시간만 저장한다. OCR 원문, 환자 정보, LLM 원문 응답과 약물 결과 값은 저장하지 않는다. 소스·설정·이미지·정답 해시 및 체크포인트 체크섬이 일치할 때만 재개한다. 중단된 문서는 OCR부터 다시 실행한다.

`serviceNoLlm`은 이미지 읽기부터 no-LLM 서비스 응답 직렬화까지다. `postOcrReplay`는 OCR 재사용 후처리이며, LLM 호출 시간은 별도 실측이다. semantic의 전체 서비스 지연을 직접 측정한 것으로 표현하지 않는다.

## 확인한 실패와 수정

1. 초기 단일 문서 실험은 함량 2개를 복구했지만 복합제 성분 하나를 제품 전체 함량으로 선택해 FP 1개가 생겼다. 서로 다른 성분 함량이 여러 개면 단일 성분 값을 채택하지 않도록 차단했다.
2. 전체 v2 실험에서 복용일수의 합쳐진 OCR 숫자 `33`, `15`를 그대로 채택해 기존 정답 2개를 훼손했다. v3의 첫 수정은 실제 메타데이터와 다른 테스트 가정 때문에 이 문제를 막지 못했다. 최종 v4는 레이아웃 셀의 `parsed_text`와 원본 블록의 차이를 확인해 합쳐진 숫자를 선택 불가 문맥으로 처리한다.
3. 독립 검토를 통해 한 블록/여러 블록의 복합제 함량, 서로 다른 숫자 블록 이어붙이기, 농도 분모를 버리는 정규화를 회귀 테스트에 추가했다. 일부만 파싱되는 함량은 채택하지 않는다.
4. 다른 행·알 수 없는 제품 제목 경계, 불필요한 근거 ID, 누락/중복 행, 숫자 일부 추출, 단위 손실, 임의 주변 문구 유출도 검증했다.
5. v4 전체 실험은 독립 검토에서 추가 문제가 확인되어 중간에 중단했다. 제품 제목 안에 여러 함량이 있는데 하나만 인용하는 선택도 차단한 v5로 전체 실험을 새로 실행했다. 제목 근거라는 이유만으로 복합 함량의 일부 선택을 허용하지 않는다.

v4 두 문서 사전 검증은 3회 모두 `54/58 → 56/58`, FP 1개 유지, 기존 정답 훼손 0개였다. 복구된 2개는 sample-08의 함량이며 sample-09의 복용일수는 보존됐다.

## 전체 최종 실측 및 적용 상태

최종 근거는 `.context/ocr-semantic-review-full-20260907-v5/summary.json`과 문서별 검증된 체크포인트다. `--resume-only` 재검증도 통과했으며 추가 공급자 호출 없이 같은 집계를 재현했다. 세 반복 모두 아래와 동일했다.

| 방식 | 보정 정답 | 정확도 | FP | 완전 일치 행 |
| --- | ---: | ---: | ---: | ---: |
| no-LLM | 273/309 | 88.35% | 8 | 54/77 |
| legacy LLM | 273/309 | 88.35% | 8 | 54/77 |
| semantic LLM | 275/309 | 89.00% | 8 | 56/77 |

매 반복에서 sample-08의 함량 2개만 복구됐고 기존 정답 훼손·새 FP는 0개였다. 해당 문서는 `31/33 → 33/33`, FP 0이다. sample-11의 추가 개선으로 중복 집계하지 않는다. 원래 정답 기준도 `272/309 → 274/309`, FP 9개 유지였다. 전체 개선은 **0.65%p**로, 큰 폭의 정확도 향상이라고 주장하지 않는다. 남은 34개 정답 필드 누락/불일치와 FP 8개는 해결되지 않았다.

실측 모델은 기존 설정의 `gpt-4o-mini`를 유지했다. legacy 실제 LLM 호출 6회, 평균 1,345ms; semantic 42회, 평균 7,985ms, 중앙값 7,754ms, 범위 4,387–17,571ms였다. 두 방식 모두 호출 실패는 0회다. 호출 대상 수가 다르므로 이 평균을 동일 문서의 배속 비교로 해석하지 않는다. 전체 no-LLM 서비스 평균은 2,591ms, 재촬영 제외 14건은 2,923ms였다. semantic 전체 서비스 시간은 별도 측정하지 않았다.

각 반복의 정확도 상승·FP 비증가 조건을 충족해 한때 워커에 semantic을 연결했으나, 속도 비용 확인 후 사용자가 적용 취소를 요청했다. `app/workers/medication_guide_ocr_worker.py`의 `review_mode="semantic"` 인자를 제거해 기존 legacy 기본 경로로 복귀했다. 실험 코드·검증 기록과 화면 표시 개선은 보존했다. 실행 중 워커는 이 작업에서 재시작하지 않았다.
