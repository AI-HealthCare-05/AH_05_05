# OCR v3.4 적응형 전처리 — 2026-09-07

## 목적과 비교 범위

906 로컬 복사본에서 기존 파이프라인을 추적하고 서로 다른 세 가설을 구현·비교했다. 전처리 밖의 약 행 파서, OCR 공급자, LLM 프롬프트, DB 모델은 변경하지 않았다. 실행 중인 서비스와 실제 `.env`도 변경하지 않는다.

원본 16장 비교의 최상위 후보는 **v3.4.1: 250/309 = 80.91%**다. v3.1.3의 239/309보다 11필드, **3.56%p** 높다. 원본 비교 재실행에서도 같은 결과가 나왔고, 사전 승격 기준과 독립 검토를 통과해 **코드 기본값으로 적용했다.** 실제 `.env`, 실행 중인 worker와 DB는 변경하지 않았다.

이는 이미 결과를 알고 있던 작은 개발 코퍼스에서의 결과다. 일반적인 최고 성능이나 새로운 병원 양식의 성능을 보증하지 않는다. 개선 대부분은 sample-03 한 장에서 발생했고, 약 이름 정확도와 precision은 소폭 하락했다.

선택 조건을 원근 보정 성공 여부로 둔 이유는, 배경이 남거나 작은 인쇄가 그대로인 전체 프레임에서 선명화가 잡음을 키울 수 있기 때문이다. 이 가설은 기존 실패 패턴에서 출발했으므로 독립 검증셋에서 발견한 규칙으로 주장하지 않는다. 경로별 픽셀 동등성 테스트로 원근 경로는 v3.2.7, fallback은 v3.1.3과 일치함을 확인한다.

극단 종횡비 입력이 문서 검출용 축소 과정에서 0px 변으로 반올림되는 기존 오류도 발견했다. 세 축소 지점에 `max(1, round(...))`를 적용했다. 일반 이미지의 기존 버전 결과는 원본 비교에서 재현됐다.

## 채점·데이터·재현성

- 기존 정답 309개 값을 변경하지 않았다. 원본 77행 × 5필드 385칸을 별도로 재검토하여 `값 존재 309 / 인쇄되지 않음 44 / 판독 불가 32`로 분류했다. 판독 불가는 없음으로 간주하지 않는다.
- 원본에서 읽을 수 있는 이름·함량·1회량·횟수·일수의 정규화 일치를 채점한다. 빠진 값/행은 FN이며 정답이 아니다. 틀린 대체 값은 FP와 FN, 추가 행/인쇄되지 않은 필드의 주장은 FP로 계산한다.
- 일반적인 일대일 행 매칭을 사용한다. 중복 예측은 재사용할 수 없다. 판독 불가 값에 대한 주장은 정오를 추측하지 않고 별도로 집계한다.
- `엄격 일치 행`은 읽을 수 있는 값이 모두 맞고, 인쇄되지 않은 값을 추가하지 않은 원본 행이다. 판독 불가 필드는 제외한다. 5필드 전부 읽히는 행만의 별도 지표도 보존한다.
- 문서 성공은 누락/추가 행 없이 모든 행이 엄격 일치하는 경우다. sample-08과 sample-11은 같은 문서 그룹으로 묶어 전체 15그룹의 macro 성공률도 계산한다. 기존/추가 8장은 요청한 기술 통계이며 서로 독립된 학습/시험 분할이 아니다.
- OCR 원문·환자 정보·이미지 사본을 저장하지 않는다. 구조화된 약 5필드, 비식별 수치, 입력/변형/코드/평가기/설정의 SHA-256만 기록한다.
- 이미지·버전·변형 단위 결과를 checksum과 함께 원자 저장한다. 완료 결과는 OCR 객체 생성 없이 재사용한다. 호출 시작 후 완료 여부가 불명확한 결과는 `.inflight`로 막고 자동 재호출하지 않는다. 손상·다른 입력·다른 코드 체크포인트는 거절한다.

## 처리 시간과 메모리

원본 각 이미지·버전의 전처리를 3회씩, 이미지와 반복마다 실행 순서를 순환해 총 192회 직렬 측정했다. OCR·테스트 등 다른 CPU 작업이 끝난 후 측정했으며 이미지별 3회 중앙값 16개를 요약했다. p95는 이 16개 값의 선형 보간 백분위다. 전체 처리 시간은 별도 실제 OCR 실행 16회의 평균/중앙값/p95이며, 이미지당 1회이므로 네트워크 잡음이 크다.

최종 측정의 후보 평균 차이는 **−8.49ms**, 이미지별 최대 증가는 +34.33ms다. 첫 실험의 3회 반복에서는 +3.15ms였으므로 후보가 더 빠르다고 주장하지 않는다. 측정 변동 범위에서 실질적인 추가 부담이 작으며 평균 증가 +100ms 목표와 +200ms 한도를 만족한다.

전체 시간은 native 서비스 분석(전처리·HTTP OCR·행 조립·검증)을 포함하고 큐 대기·DB·사용자 편집·LLM을 제외한다. 이번 harness는 이미지별 HTTP 클라이언트를 생성하므로 예전 공유 클라이언트 실험과 절대 시간을 직접 합치지 않는다. 비교군 내부는 같은 프로토콜이다. 실제 실행 서비스의 지연 SLA를 입증한 결과는 아니다.

최대 입력 경계는 OCR 없이 새 자식 프로세스별 10,000×4,000 합성 이미지를 처리했다. 출력은 두 버전 모두 4096×1596, 좌표 왕복은 통과했다. peak working set은 기준선 511,197,184바이트, 후보 511,680,512바이트로 **+483,328바이트(약 0.46MiB)**다. 기준선 +20% 및 +64MiB 이내 조건을 모두 만족한다. 이 값은 시험 프로세스 전체의 메모리이며 운영 동시 처리 메모리 보장은 아니다.

## 결정론적 강건성 테스트

원본 각각에 +4° 회전(확장된 흰 배경), 모서리 3% 원근 변형, 좌→우 0.65→1.0 밝기 변화, Gaussian σ=0.65 흐림, 0.7배 축소를 각각 적용했다. 변형 뒤 JPEG 품질 95로 인코딩했으므로 미세 압축 변화도 포함된다. 두 버전에는 같은 변형 바이트를 제공했다. 음의 회전은 합성 안전 테스트만 포함하며 실제 OCR 변형 비교에는 포함하지 않았다.

각 변형은 원본 정답 309필드를 그대로 사용한다. 축소·흐림 뒤 사람이 새로 읽을 수 없는 부분까지 원본 복구 목표로 남기므로 절대 점수는 보수적인 스트레스 지표다. 같은 원본에서 파생된 80장은 새로운 독립 문서 80장이 아니다.

160회 서비스 분석 중 실제 OCR은 94회, LLM은 0회였다. 후보 때문에 추가된 재촬영이나 2개 이상 정답 행을 잃은 문서는 없었다. 회전·원근의 낮은 절대 성능은 **기존 문서 검출/품질 게이트의 큰 공통 약점**이다. 후보의 회귀가 없다는 결과를 회전 문제 해결로 해석하면 안 된다.

변형에서 달라진 위치는 흐림 sample-09(+24필드, +6추출 행), 원근 sample-13(+2필드, +1추출 행), 그림자 sample-05(+1필드, +1엄격 행), 그림자 sample-13(+1필드·+1추출 행이지만 −1엄격 행)이다. 나머지 정답 수와 재촬영 판정은 같았다. 특정 변형 결과를 본 뒤 후보 파라미터를 다시 조정하지 않았다.

## 미해결 실패와 범위

sample-04는 세 새 가설로 해결하지 못했다. 전체 프레임 경로에서 OCR 호출은 성공하지만 구조화 약 행이 0이다. 문자 deskew 단독으로도 이전 실험에서 해결되지 않았다. 공급자 결과와 행 후보 조립 경계의 별도 분석이 다음 병목이며, 이번에는 파서 변경으로 전처리 점수를 올리지 않았다.

sample-06·14는 `document_crop_suspected`가 유지된다. 원본에 없는 글자를 복원하거나 잘림 안전 조건을 임의로 해제하지 않았다. sample-12의 제품명/성분명 선택과 나머지 이름 오류는 전처리만으로 해결되지 않았다. 공급자·파서·LLM 변경은 별도 작업이다.

다음 전처리 병목은 약한 회전·원근 변화에서의 잘림 의심 판정이다. 이번 후보는 이 게이트를 바꾸지 않았다. 다음 실험은 새로운 독립 문서를 확보한 뒤 실제 crop 누락과 검출 오판정을 별도 라벨링해야 한다. 알려진 16장의 오류만 피하도록 게이트를 완화하는 것은 안전한 해결이 아니다.

`Config`, `preprocess_image`와 `MedicationOcrV3Service`의 기본값, `.env.example`을 v3.4.1로 맞췄다. 기본값 연결 테스트 3개가 이전 v3.1.3에서 실패하는 것을 먼저 확인한 뒤 수정했다. 명시적 버전 선택과 v3.1.3 fallback은 유지한다.

승격 뒤 기본값 리터럴을 제외한 전처리 알고리즘은 측정 시점과 같다. `promotion-code-audit.json`은 두 앱 파일과 config에서 기본값을 되돌린 바이트의 SHA-256이 측정 manifest와 정확히 일치함을 증명한다. 평가 앱 해시 `817c8e8ffa6832b34f36b1325863506d3559751a610e44b471fcd18fff44ef4d`에서 승격 해시 `8b540b0a3ffdb400814a36e8d31b46c338dc8b0e098829381be88fe8b55bdc98`로 바뀐 이유는 기본값 선택뿐이다. 공급자·파서·LLM 본문은 변경하지 않았다.

원본 `.env`에 버전이 명시되어 있으면 새 코드 기본값보다 우선한다. 이번에는 운영 전환·worker 재시작·DB migration을 실행하지 않았다. 별도 운영 반영 후 새로운 문서에서 회귀가 확인되면 명시적 `OCR_PREPROCESS_VERSION=v3.1.3`으로 되돌릴 수 있다. 현재 사용자의 재확인 흐름은 유지한다. 자동 모니터링이나 배포 작업을 새로 만들지는 않았다.

### 테스트와 검토 내역

- 승격 후 OCR·전처리·API·worker·설정·평가기·엄격 무결성 테스트 **305개 통과(20.07초)**. 이미지 좌표 왕복, 마스크, 점선/표/잡음, 수평 보존, 작은 글자, 그림자/흐림/저해상도, 1×4096·4096×1, 빈/손상 입력과 상한을 포함한다.
- 과거 OCR migration 테스트 4개까지 포함한 최종 확장 실행은 **307개 통과·2개 실패(22.88초)**다. 실패는 `test_async_ocr_migration_follows_nutrient_standard_and_captures_merged_models`와 `test_migration_captures_current_ocr_v3_model_state`이며, 과거 migration 7/21의 전체 모델 스냅샷을 22~31 변경 후의 현재 모델과 완전 동일 비교한다. 독립 검토에서 이번 v3.4와 무관함을 확인했다. 모델·migration·해당 테스트는 바꾸지 않았다. 저장소 전체 검사가 완전히 녹색이라고 주장하지 않는다.
- 수정 범위 15개 Python 파일의 Ruff lint/format과 `git diff --check`는 통과했다. 새 `adaptive.py`의 Mypy도 통과했다. 추가로 기존 `preprocess.py`까지 타입 검사하면 `_inverse`의 NumPy 역행렬 타입 1건과 `_natural_size`의 scalar 곱 타입 2건이 남는다. 두 함수 AST는 원래 903 소스와 동일하며 이번 변경이 아니다. 미실행 검사를 통과로 기록하지 않았다.
- 실제 API/worker 단위·통합 테스트는 실행했지만 실행 중인 서비스를 재배포하거나 브라우저 UI를 변경하지 않았다. UI 전 구간 E2E를 새로 수행한 것은 아니다.
- 합성 문서의 원근 보정 전/후 및 개인정보 마스크를 메모리에서 시각 확인했다. 실환자 이미지나 OCR 원문 사본은 만들지 않았다.
- 처음 발견한 점선/잡음 확대 오인, 극단 비율 0px 축소, 실패한 메모리 검증의 캐시 재실행 우회를 각각 실패 테스트 후 수정했다.
- 범용 평가기만으로는 예정된 비교군/반복의 누락을 감지할 수 없다는 검토 결과에 따라 별도 엄격 검증기를 추가했다. 현재 코드/원본, 3회 유한 시간, 정확한 비교 격자, 모든 checksum·payload·provenance, 잔존 `.inflight` 없음, 추가 호출 없음이 승격 조건이다. 변형의 반복 전처리 시간은 측정하지 않았으며 `--without-timings`로 명시한다.
- 채점기 최종 Ruff 포맷만 보완했다. 전후 AST 해시 `375073dfe242225118d0fb30f484f1e829e6c2735b91b72d36fe089a1c3f674e`가 같고, 기존 저장 결과로 모든 보고서를 다시 계산했다. 정답·매칭·점수 로직과 OCR 호출은 바꾸지 않았다.
- Code review: **harness-native fallback**. Git 미추적 새 파일과 선행 사용자의 변경이 섞여 있어 staging 없이 표준 branch diff로 정확한 범위를 만들 수 없었다. 파일 소유권을 나눈 재사용/품질/효율 검토와 명시적 경로의 독립 검토를 사용했다. 일반 branch 전체를 리뷰했다고 주장하지 않는다.

이번 작업의 실제 호출 합계는 **서비스 분석 320회, OCR 234회, LLM 0회**다. 구성은 첫 가설 비교 96/84, 최종 원본 비교 64/56, 변형 비교 160/94(서비스/OCR)다. 별도 반복 전처리는 288+192=480회이며 OCR을 호출하지 않는다. 재개·해시 검증·점수 재계산·승격에는 추가 OCR 호출이 없었다.
